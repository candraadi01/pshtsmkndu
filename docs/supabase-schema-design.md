# Rancangan final schema Supabase — Phase 2

Status: **menunggu persetujuan; belum diterapkan**
Dasar data: audit `psht.sql`, snapshot kandidat 30 Mei 2025
Draft SQL: `supabase/migrations/0001_initial_schema.sql`

## Batas rancangan

Dokumen ini menetapkan rancangan schema awal berdasarkan dump kandidat, migration, model, controller, dan UI Laravel. Snapshot bukan bukti database produksi terbaru. Draft belum pernah dijalankan ke Supabase dan tidak mengimpor data, membuat akun Auth, mengunggah media, atau mengubah UI.

Tabel infrastruktur Laravel (`cache`, `cache_locks`, `migrations`, `password_reset_tokens`, `personal_access_tokens`, dan `sessions`) tidak dibuat di Supabase. Kebutuhan cache/session/Auth akan ditangani oleh platform atau rancangan terpisah.

## Keputusan final yang diterapkan dalam draft

1. `people.tipe` memakai `pelatih`, `warga`, dan `siswa`.
2. `people.sabuk` tidak dibuat karena tidak ada pada dump.
3. Role kanonis adalah `admin`, `super_admin`, dan `user`.
4. Import data kelak harus mengubah `super admin` menjadi `super_admin`; draft ini tidak mengimpor row.
5. `artikel.status` memakai `draft`, `published`, dan `archived`.
6. `page_settings` mencakup seluruh field dalam dump dan dibatasi maksimum satu row.
7. `pengumuman.aktif` tidak dibuat.
8. Nama tabel dipertahankan sebagai `dokumen` dan `tipe_dokumen`.
9. Primary key konten memakai `bigint generated by default as identity`, sehingga ID legacy dapat dimasukkan eksplisit saat migrasi data.
10. Penulis artikel dipisahkan menjadi `legacy_user_id bigint` dan `author_id uuid`.
11. Timestamp aplikasi memakai `timestamptz`.
12. Tidak ada akses tulis untuk role `anon` maupun `authenticated` pada draft ini.

## Rancangan relasi Auth

```text
auth.users (dikelola Supabase; kosong pada tahap schema)
    │ 1
    │
    └── 0..1 public.profiles
                 id uuid PK/FK -> auth.users.id
                 role: user | admin | super_admin
                 │
                 ├── 0..n public.legacy_users.profile_id
                 └── 0..n artikel.author_id

public.legacy_users
    id bigint (ID users Laravel)
    role: user | admin | super_admin
    │
    └── 0..n artikel.legacy_user_id

artikel.author_id ───────────────> profiles.id (nullable)
artikel.legacy_user_id ─────────> legacy_users.id (nullable)
CHECK: sedikitnya salah satu identitas penulis harus tersedia
```

Alasannya:

- Password hash Laravel dan `remember_token` tidak dimasukkan ke schema baru.
- Artikel lama dapat diimpor dahulu dengan `legacy_user_id` tanpa akun Supabase Auth.
- Setelah akun Auth dibuat pada tahap yang disetujui terpisah, `legacy_users.profile_id` dan `artikel.author_id` dapat diisi tanpa menghilangkan atribusi legacy.
- `artikel.author_id` menunjuk `public.profiles(id)`, bukan langsung ke `auth.users(id)`. Ini membuat relasi konten bergantung pada identitas aplikasi yang memuat role/display name, sementara integritas terhadap akun Auth tetap dijamin oleh PK/FK satu-ke-satu `profiles.id → auth.users.id`.
- `author_id` menggunakan `ON DELETE SET NULL`; `legacy_user_id` memakai `ON DELETE RESTRICT`. Artikel tidak ikut terhapus ketika akun Auth dihapus, sedangkan penghapusan record legacy ditahan selama masih dirujuk.
- Check constraint `artikel_author_present` mencegah artikel tanpa jejak penulis.

## Constraint dan index

- Check constraint: role, `people.tipe`, `people.jenis_kelamin`, status artikel, `view_count >= 0`, dan keharusan identitas penulis.
- Unique: `profiles.id`, `legacy_users.id`, `legacy_users.email`, `legacy_users.auth_user_id`, dan `artikel.slug`.
- Unique expression index `page_settings_singleton_idx` memastikan maksimum satu row tanpa mengganti ID legacy.
- Index query publik: artikel berdasarkan status/tanggal, status/view count, pengumuman terbaru, ekstrakurikuler terbaru, gallery terbaru, image per gallery, people per tipe/nama, serta dokumen per tipe.
- Index FK eksplisit ditambahkan karena PostgreSQL tidak otomatis membuat index pada kolom referencing FK.
- Trigger terbatas menjaga `updated_at = now()` pada setiap update; fungsi trigger tidak dapat dieksekusi langsung oleh role client.

## Keamanan dan RLS

Semua tabel `public` mengaktifkan Row Level Security. Draft mencabut seluruh privilege dari `anon` dan `authenticated` sebelum memberikan akses baca minimum.

### Boleh dibaca anonim

- `artikel`
- `pengumuman`
- `ekstrakurikuler`
- `galleries`
- `images`
- `page_settings`
- `tipe_dokumen`
- `dokumen`
- Hanya kolom `id`, `nama`, `tipe`, dan `foto` pada `people`

Policy artikel bukan policy umum: role client hanya dapat membaca row dengan `status = 'published'`. Artikel `draft` dan `archived` tidak terlihat bagi `anon` maupun `authenticated` pada rancangan ini.

### Tidak boleh dibaca anonim

- `profiles`
- `legacy_users`
- `people.jenis_kelamin`
- `people.alamat`
- `people.no_hp`

Tidak ada `INSERT`, `UPDATE`, atau `DELETE` yang diberikan kepada `anon` maupun `authenticated`. Kebijakan admin/write sengaja belum dibuat sampai Auth dan otorisasi dirancang serta disetujui.

### Hasil audit akses `page_settings` dan dokumen

Grant baca anonim untuk `page_settings`, `tipe_dokumen`, dan `dokumen` dipertahankan berdasarkan bukti source Laravel, bukan asumsi:

- Middleware `HandleInertiaRequests` membagikan seluruh `PageSetting::first()` pada setiap respons Inertia.
- Field `page_settings` dipakai oleh halaman publik Home, Registrasi, Struktur Organisasi, dan Header.
- Route `/dokumen/{id}` didefinisikan di luar grup middleware `auth`.
- Halaman Dokumen menyediakan tautan langsung `/storage/{path}` untuk pengunduhan.

Mencabut akses tersebut sekarang akan menghilangkan konten Home/Registrasi/Struktur atau memutus daftar dan unduhan dokumen ketika aplikasi beralih ke Supabase. Seluruh field `page_settings` berisi konfigurasi konten publik pada snapshot; tidak ditemukan credential atau data akun. Walau demikian, isi HTML `syarat_pendaftaran`, URL video, serta setiap dokumen/media tetap harus ditinjau sebelum produksi karena kontennya dapat berubah setelah snapshot.

### Aturan query `people`

Privilege database membatasi client pada `id`, `nama`, `tipe`, dan `foto`. Query aplikasi **tidak boleh menggunakan `select('*')` pada `people`**. Query harus menyebut kolom secara eksplisit, misalnya `select('id,nama,tipe,foto')`; query statistik cukup memilih `id` dengan filter `tipe`. Kolom `jenis_kelamin`, `alamat`, dan `no_hp` tidak diberikan kepada `anon` maupun `authenticated`.

## Risiko migrasi

1. Dump bertanggal 30 Mei 2025 mungkin bukan snapshot terbaru.
2. Backend produksi terakhir belum terkonfirmasi antara MySQL dan SQLite.
3. Timestamp historis tidak memiliki zona waktu yang dapat dibuktikan; konversi ke `timestamptz` memerlukan asumsi zona yang disetujui.
4. Normalisasi `super admin → super_admin` dapat memengaruhi akses; harus divalidasi sebelum Auth aktif.
5. `page_settings.syarat_pendaftaran` NOT NULL pada dump; draft mempertahankannya, sehingga import/new insert harus menyediakan nilai.
6. Singleton `page_settings` sebelumnya hanya dijaga aplikasi; unique index baru dapat menolak row kedua.
7. Dual-author artikel memerlukan urutan backfill yang tepat sebelum akun Auth ditautkan.
8. ID identity sequence harus diselaraskan setelah import eksplisit agar insert berikutnya tidak bentrok.
9. Path media tetap berupa path Laravel pada awalnya; perubahan ke URL Cloudinary bukan bagian migration schema.
10. `ON DELETE CASCADE` pada images dan dokumen mengikuti Laravel, tetapi penghapusan parent bersifat destruktif.
11. Akses publik ke nama/foto people harus dikonfirmasi dari sisi privasi sebelum produksi.
12. File media/dokumen lokal belum diaudit satu per satu untuk data pribadi.

## Rencana validasi pada Supabase development

Validasi berikut baru dijalankan setelah draft disetujui dan hanya pada project development kosong:

1. Pastikan project bukan production dan catat project reference yang disetujui.
2. Jalankan migration melalui tooling Supabase pada database development kosong.
3. Verifikasi semua tabel, kolom, tipe, default, constraint, FK, dan index melalui katalog PostgreSQL.
4. Pastikan `auth.users` tetap kosong dan tidak ada akun dibuat.
5. Uji insert sintetis di dalam transaction lalu `ROLLBACK`:
   - role valid diterima dan role lain ditolak;
   - tipe/status/gender valid diterima dan nilai lain ditolak;
   - `view_count < 0` ditolak;
   - artikel tanpa kedua author ditolak;
   - artikel legacy-only dan auth-only diterima bila parent tersedia dalam transaction;
   - row kedua `page_settings` ditolak.
6. Uji FK dan delete behavior di dalam transaction lalu rollback.
7. Uji role `anon`: SELECT tabel publik berhasil, SELECT PII gagal, dan seluruh write gagal.
8. Uji role `authenticated`: tidak memperoleh write sebelum policy Auth dibuat.
9. Jalankan schema lint/diff dan pastikan tidak ada perubahan tak terduga pada schema `auth`.
10. Simpan hasil validasi sebagai laporan; jangan mengimpor dump pada langkah ini.
